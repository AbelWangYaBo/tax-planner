# 个税测算与年终奖方案对比

一个**零依赖、单页可运行**的中国大陆个人所得税测算工具。输入工资、n 薪、年终奖、劳务报酬等数据，输出预计到手收入、全年税额、汇算补退税，并给出**税额最小的年终奖计税方案**。

## 快速开始

直接用浏览器打开 `index.html` 即可，无需安装、无需构建、无网络请求：

```bash
open index.html          # macOS
# 或双击 index.html
```

跑引擎自检（257 项断言）：

```bash
node test.js
```

## 解决什么问题

年终奖的计税方式是一次**最优化决策**，而不是简单套公式：

| 计税方式 | 规则 | 特点 |
|---|---|---|
| 单独计税 | 奖金 ÷ 12 查月度税率表，速算扣除数只扣一次 | 可多享受一次速算扣除数，但有税率盲区 |
| 并入综合所得 | 与工资合并适用年度税率表 | 无盲区，但可能推高整体税率 |
| **拆分发放** | 一部分单独计税 + 一部分并入 | 通常最优，但**必须在发放前安排** |

本工具会把三种方案全部算出来，并给出最优拆分点。

## 支持的输入

### 任职单位（可增删多个）

| 类型 | 说明 | 备注 |
|---|---|---|
| **主工作** | 必填，享受专项附加扣除 | 省份/城市、月税前工资、任职月数、社保与公积金比例、n 薪、年终奖 |
| **换工作** | 年内跳槽，按新单位独立缴社保公积金 | 与主工作同样的字段 |
| **多处任职** | 同时打两份工，社保公积金**不重复**缴纳 | 只需月税前工资与任职月数 |

点击「＋ 增加任职单位」添加，每张卡片可删除。**月税前工资与年终奖默认留空**，避免未填写时算出误导性结果。

### 缴费基数按城市自动带出

选择「省份 → 城市」后，社保与公积金的基数上下限自动填入，无需手工查询：

- 基数 = 月工资，再按当地**下限保底、上限封顶**，命中时界面标注「已按上限封顶 / 已按下限保底」
- 社保与公积金比例可分别调整（社保默认 10.5% = 养老 8% + 医疗 2% + 失业 0.5%；公积金默认取当地允许的最高值）
- 公积金是**双边**缴存：勾选「单位缴存与个人一致」时只填一个比例，取消勾选可分别填写
- 公积金支持两种缴存方式：
  - **按比例**（默认）：缴存基数 = 月工资，按城市上下限保底 / 封顶，再乘以比例
  - **按金额**：直接填个人 / 单位月缴额，**不套用城市基数上下限**。用于缴存基数与实际工资不一致的场景——例如工资 15,000 却按 25,000 缴纳，超出部分（含单位侧）由个人承担

### 收入方式：固定月薪 / 逐月录入

每个任职单位可选两种录入方式：

| 方式 | 适用 | 录入内容 |
|---|---|---|
| **固定月薪** | 收入平稳 | 月基本工资 + 月补贴/补助 两个字段 |
| **逐月录入** | 销售、提成、项目制等浮动收入 | 每月「基本工资 / 奖金提成 / 补助」三列，共 12 行 |

固定月薪把「基本工资」和「补贴/补助」分开填，是因为这两者**个税口径一致、社保口径常常不一致**（见下节）。

逐月录入支持：
- **均分填充**：按第一个月的基本工资铺满全年
- **下载模板**：导出 CSV（Excel / WPS 双击可开）
- **导入表格**：直接导入 `.csv` 或 `.xlsx`，按表头自动识别列

模板格式：

```
月份,基本工资,奖金提成,补助
1,10000,0,1000
2,10000,5000,1000
...
```

### 缴费基数：与当月工资解耦

这是浮动收入最容易算错的地方，有两条规则要分开看：

**1. 时间维度**：社保与公积金的缴费基数，是**上年度月平均工资**，一年核定一次，不随当月收入浮动。

**2. 构成维度**：**补助、奖金提成通常不计入缴费基数**。法定口径虽是「上年月均全额工资」，但很多单位实际按基本工资或某个固定基数申报——这一点因单位而异，工具不做假设。

所以每个任职单位都有一个独立的「缴费基数（月）」：

| 填法 | 行为 |
|---|---|
| **留空（默认）** | 取**基本工资**（逐月模式取基本工资列的月均），**不含**奖金提成与补助 |
| **填写数字** | 以该值为准，再按所选城市的上下限保底 / 封顶 |

默认取基本工资而不是全额工资，是因为「不含补助」在实际中更常见；如果你们单位按全额工资申报，把基数改成税前合计即可。

举例：

| 项目 | 金额 |
|---|---|
| 月基本工资 | 25,500 |
| 月补贴/补助 | 3,000 |
| 月税前合计（个税基数） | **28,500** |
| 缴费基数（社保 / 公积金） | **25,500** |

个税按 28,500 算，社保公积金按 25,500 算。某销售 2024 年月均收入 12,000，2025 年无论哪个月发多少提成，都按 12,000 的基数缴——在逐月录入里填 12 个月收入，再把「缴费基数」填 12,000 就是准确口径。

### 其他

- **n 薪**：13/14/15/16 薪，可选择计入工资或计入全年一次性奖金
- **年终奖**：按任职单位分别填写，合并进奖金池（全年一次性奖金单独计税一年只能用一次）
- **专项附加扣除**：子女教育、房贷利息、住房租金、赡养老人、继续教育、大病医疗等（按月录入）
- **其他扣除**：个人养老金 12,000、商业健康险 2,400 等（按年录入）
- **劳务报酬 / 稿酬 / 特许权使用费**：年度总额 + 收款笔数（笔数默认 0，填写总额后自动置为 1）
- **股权激励**：股票期权、限制性股票等，单独计税

### 年中基数调整

**同一年内基数并不恒定**，这是很容易算错的地方。各地调整月份不同：

| 省份 | 调整月 | 调整前 → 调整后 |
|---|---|---|
| 北京 | 7 月 | 7,162–35,811 → 7,270–36,348 |
| 山西 | 1 月 | 4,198–20,991 → 4,244–21,219 |
| 天津 | 9 月 | 5,124–25,620 → 5,180–25,902 |
| 广东 | 7 月 | 5,510–27,549 → 5,521–27,603 |

引擎按月取基数：1–6 月用调整前，7–12 月用调整后，**逐月累计预扣**，而不是拿一个数乘 12。

`cities.js` 里每省存 5 个值：

```js
{ name: '北京市', social: [7162, 35811, 7270, 36348, 7], cities: [...] }
//                        ↑前下限 ↑前上限 ↑后下限 ↑后上限 ↑调整月
```

公积金额外带比例区间与备注：

```js
'北京': [2540, 35811, 2540, 36348, 5, 12, 7, ''],
//       前下限 前上限 后下限 后上限 比例↓ 比例↑ 调整月 备注
```

### 公积金未收录的城市

公积金缴存基数由**各城市公积金管理中心单独公布**，全国 300+ 城市逐年各发各的，没有统一的汇总源。因此：

- 未收录的城市**仍可选**，社保正常按省级两段数据计算
- 界面提示「公积金未收录」，并**就地提供下限 / 上限输入框**
- 不填则不封顶

扩充只需在 `HOUSING` 里加一行，无需改代码。

### 采集流水线（collector/）

基数不靠聚合站，由 `collector/` **只访问各地公积金中心 / 人社厅（局）官网**逐城采集，
每条数据都带文号、原文链接、抓取时间与原文片段，可逐条回溯：

```bash
node collector/run.js --kind=all --year=2026 --prev=2025   # 公积金 + 社保，两个年度
node collector/run.js --only=上海,北京 --kind=housing        # 只补某几个城市
node collector/run.js --ingest=data/ai-ingest.jsonl          # 回灌「AI 读 PDF」的结果
node collector/build-cities.js                              # 生成引擎用的 cities.js
node collector/server.js                                    # 起本地服务，页面按钮可用
node collector/report.js                                    # 覆盖报告 → data/COVERAGE.md
node collector/test-extract.js                              # 抽取器回归（真实原文 10 段）
```

**为什么不是「一个城市一组上下限」**：每年 7 月前后用的是两个年度的基数，且各地切换月份不同
（杭州/北京/广州/深圳 7 月、南宁 1 月、部分省份社保 1 月）。所以数据按**生效时间段**存：

```json
{"from":"2026-07-01","to":"2027-06-30","min":2660,"max":42151,
 "docNo":"杭公积金〔2026〕21号","source":"https://gjj.hangzhou.gov.cn/…",
 "status":"verified","confidence":"high","via":"ai-pdf"}
```

引擎按月份取段，**切换时间成为数据而不是假设**；历史观测只追加不覆盖
（`data/observations.jsonl`），因此往年的口径永远查得到。

页面顶部有「检查更新」：直接双击打开时提示需要本地服务，测算照常；
`node collector/server.js` 后访问 `http://127.0.0.1:8787`，点按钮即触发采集（Alt + 点击 = 全量）。

PDF 正文一律交给 AI 识别：流水线**不下载 PDF、不做本地 OCR**，只把附件链接写进
`data/ai-queue.json`，由具备 PDF 解析能力的调用方读出文本后回灌，本机只留 KB 级文本。

详见 [collector/README.md](./collector/README.md)。

## 合法节税建议

每次测算后会自动生成一组建议，全部基于**法定扣除**与**计税方式选择**，不涉及虚列扣除等违法操作。

| 建议 | 触发条件 | 节税额算法 |
|---|---|---|
| 用足个人养老金 | 其他扣除 < 12,000 | `税(基数) − 税(基数 − 补足额)` |
| 提高公积金比例到 12% | 个人比例 < 12% 且为按比例模式 | 同上，按新增扣除额计算 |
| 年终奖拆分 | 最优解是中间拆分点 | 与二选一中最省方案的差额 |
| 年终奖调出盲区 | 奖金落在盲区且无更优拆分 | **净收益** = 少缴税额 − 少拿的奖金 |
| 专项附加扣除核对 | 未填 / 可复核 | 定性提示 |
| 汇算退税提醒 | 预缴 > 应纳 | 定性提示 |

节税额不是简单乘边际税率，而是精确计算 `annualTax(基数) − annualTax(基数 − 新增扣除)`，因此跨档时会自动反映真实效果。

### 关于 AI / 联网

工具本身**不联网、不调用任何 AI 或搜索接口**，原因是：

1. 静态页面里嵌入 API Key 等于公开泄露；
2. 工资、奖金、家庭扣除信息属于高敏感数据，不应在未经明确同意的情况下发往第三方；
3. 纯前端页面无法绕过 CORS 直连搜索 / 大模型服务。

替代方案是「**复制 AI 咨询提示词**」按钮：把当前测算结果与已识别建议打包成一段结构化提示词，由你自行粘贴到任何 AI 工具里继续追问。数据是否外发由你决定。

## 计算规则

### 综合所得年度税率表

| 级数 | 全年应纳税所得额 | 税率 | 速算扣除数 |
|---|---|---|---|
| 1 | ≤ 36,000 | 3% | 0 |
| 2 | 36,000 – 144,000 | 10% | 2,520 |
| 3 | 144,000 – 300,000 | 20% | 16,920 |
| 4 | 300,000 – 420,000 | 25% | 31,920 |
| 5 | 420,000 – 660,000 | 30% | 52,920 |
| 6 | 660,000 – 960,000 | 35% | 85,920 |
| 7 | > 960,000 | 45% | 181,920 |

### 工资薪金：累计预扣法

```
累计应纳税所得额 = 累计收入 − 5,000×任职月数 − 累计专项扣除 − 累计专项附加扣除 − 累计其他扣除
本月应预扣税额   = 累计应纳税所得额 × 预扣率 − 速算扣除数 − 累计已预扣税额
```

预扣率使用上表的年度税率表。全年累计结果与汇算结果一致（无其他所得时补退为 0）。

### 全年一次性奖金（单独计税）

```
适用税率、速算扣除数 = 月度税率表[奖金 ÷ 12]
应纳税额 = 奖金 × 适用税率 − 速算扣除数
```

**关键**：除以 12 只为查表定位税率，速算扣除数只扣一次。这正是税率盲区的成因。

### 劳务报酬 / 稿酬 / 特许权使用费

| 项目 | 收入额 | 预扣率 |
|---|---|---|
| 劳务报酬 | ≤4,000：收入−800；>4,000：收入×80% | 20% / 30% / 40%（速算扣除 0 / 2,000 / 7,000） |
| 稿酬 | （收入−800 或 收入×80%）× 70% | 20% |
| 特许权使用费 | 同劳务报酬 | 20% |

汇算时按「收入额」并入综合所得。

### 股权激励

按《财政部 税务总局公告 2023 年第 25 号》，**不并入**当年综合所得，全额单独适用**年度**综合所得税率表（不除以 12）：

```
应纳税额 = 股权激励收入 × 适用税率 − 速算扣除数
```

同一纳税年度内多次取得的，合并计算。

### 汇算清缴

```
综合所得收入额 = 工资薪金 + 劳务(收入额) + 稿酬(收入额) + 特许权(收入额) + 并入的奖金
应纳税所得额   = 综合所得收入额 − 60,000 − 专项扣除 − 专项附加扣除 − 其他扣除
应补(退)税     = 全年应纳税额 − 全年已预缴
```

## 方案寻优算法

目标函数（`x` 为单独计税的奖金部分，`B` 为奖金总额，`S` 为不含奖金的综合所得应纳税所得额）：

```
f(x) = 单独计税税(x) + 综合所得年度税(S + B − x),  x ∈ [0, B]
```

两个税函数在各税率区间内都是 `x` 的一次函数，因此 `f` 在相邻断点之间**线性**，最小值必在端点取得。断点只有两类：

1. `x` 自身跨过月度税率表界限 → `x = 36,000 / 144,000 / 300,000 / 420,000 / 660,000 / 960,000`
2. 并入部分推动综合所得跨过年度表界限 → `S + B − x ∈ {36,000, …, 960,000}`

枚举这些断点即可得到全局最优，无需暴力搜索。`test.js` 中用 50 组参数对比了断点枚举与暴力扫描，结果一致。

> 注：月度税率表在临界点处**不连续**（速算扣除数按全额奖金抵扣，而非 12 倍档位），所以断点本身取左极限值——枚举时直接取断点即为该侧最优。

## 年终奖税率盲区

落入以下区间时，**多发反而少拿**（税后收入低于区间起点）：

| 临界点 | 盲区上界 | 盲区宽度 |
|---|---|---|
| 36,000 | 38,566 | 2,566 |
| 144,000 | 160,500 | 16,500 |
| 300,000 | 318,333 | 18,333 |
| 420,000 | 447,500 | 27,500 |
| 660,000 | 706,538 | 46,538 |
| 960,000 | 1,120,000 | 160,000 |

上界按 `U = (T − 税(T) − 速算扣除数') / (1 − 税率')` 计算，其中 `'` 表示跳档后的档位。

## 口径与假设

请在使用前了解这些约定，它们会影响结果的解读：

1. **预缴口径**：假设工资按累计预扣法预扣、年终奖按「单独计税」预扣。汇算补退金额以此为基准计算。
2. **方案的可行性差异**：
   - 方案 A（全部单独）与方案 B（全部并入）可在**年度汇算时**事后切换；
   - 方案 C（拆分）**必须**在奖金发放前确定发放结构，汇算阶段无法追溯拆分。因此方案 C 的补退数字是「若已按该结构预缴」的差额，仅作参考。
3. **社保与公积金**：基数上下限由所选城市的 `cities.js` 数据带出，基数 = 月工资并按上下限保底 / 封顶。公积金上下限未收录的城市不做封顶。
   - 公积金若选「按金额」，则跳过基数与比例的推算，直接以填写的月缴额计入；此时个人部分仍可作为专项扣除，单位部分仍只进账户。
   - 公积金双边的**单位缴存部分不进入个人工资**，因此既不增加「到手现金」，也不能作为专项扣除抵税；它只体现为公积金账户余额的增加。
   - 公积金个人缴存虽从税前扣除（因此减少个税），但进入本人账户，属于资产而非消费，所以从「到手现金」中剔除、单独列示。
4. **劳务/稿酬/特许权**：给定年度总额与笔数，按等分模拟每笔预扣。笔数会影响预扣税额（800 元固定减除的门槛效应），不影响汇算收入额。
5. **多个任职单位**：每个单位各自按 5,000 元/月减除费用预扣，汇算时全年只能扣 60,000，因此多处任职与年内换工作**通常都会补税**——这是真实规则，不是计算错误。专项附加扣除只在主工作处扣除。
   - **换工作**与**多处任职**的区别只在社保公积金：换工作会在两个城市/单位各缴一份，多处任职不重复缴。
6. **年中间断任职**：预缴按实际月数扣 5,000/月，汇算按全年 60,000 扣，差额会体现为退税——这是真实规则，不是计算错误。
7. **股权激励**：按现行政策强制单独计税，未提供「并入综合所得」的选项。
8. **政策时效**：年终奖单独计税与股权激励单独计税政策均执行至 **2027-12-31**，到期后规则可能变化。税率表集中在 `tax-core.js` 顶部，便于替换。

## 已知限制

- 各单位奖金合并为一个奖金池、只做一次「单独计税 / 并入」决策，符合「一年只能用一次」的约束；但无法表达分次发放、跨年分摊等细节
- 未处理全年一次性奖金与「低价售房」「解除劳动关系一次性补偿」等其他单独计税项目
- 未处理境外所得税收抵免、公益慈善捐赠扣除、税收优惠园区等特殊情形
- 定位采用「最近收录城市」匹配：若所在城市未收录（如无锡、保定），会落到邻近的已收录城市，结果可能偏差，请核对手动选择
- 未对接真实税务系统，不生成申报表

```
tax-planner/

└── README.md      本文档
```

`tax-core.js` 的 API：

```js
const TaxCore = require('./tax-core.js');

TaxCore.compute(input);        // 完整测算，返回方案对比与明细
TaxCore.annualTax(200000);     // 综合所得年度应纳税额
TaxCore.bonusSeparateTax(36000); // 年终奖单独计税税额
TaxCore.optimizeSplit(100000, 36000); // 最优拆分 { x, totalTax }
TaxCore.blindZones();          // 年终奖盲区区间
TaxCore.simulateWage(opts);    // 逐月累计预扣模拟
```
